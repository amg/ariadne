Load testing architecture: generators, supervision, records and verdicts

How a load run is driven, watched, recorded and judged, on aws-prod and on the home machine (cubi), and why the harness is shaped the way it is. What aws-prod itself is made of is in AWS-PROD-ARCHITECTURE.html, and how it is raised is in AWS-PROD-DEPLOYMENT.html. The commands are in infra/README.md. <project> stands for the operator's AWS_PROD_PROJECT.

1. The short version

A load run is a fleet of generators. Each one is a single Node process that plays a few thousand virtual users: they sign in, keep a tab's push stream open, and some of them chat. On aws-prod the generators are small Fargate tasks, on Spot, in a stack and network of their own. They all leave that network through one NAT gateway with one fixed address. They reach the app either directly at its load balancer, presenting a client certificate, or through Cloudflare as real users do. On the direct path the load stack itself lets its one address into the origin, so the way in lasts exactly as long as the stack.

A supervisor in the load harness runs on the operator's machine. It starts the generators, watches them through ECS, and starts a lost one again on the same slice of users. It is part of one load command, which opens the run, runs the generators, and however they end, stops every generator, seals the run and rebuilds it. A safety net in AWS deletes whatever outlives its time.

Every fact is written once, as a log line. That covers each request a generator makes, each exchange and job the backend handles, and a line of running state every few seconds. CloudWatch Logs keeps each line, and the same line carries an Embedded Metric Format block, so CloudWatch also turns it into a metric for the live dashboard and the terminal monitor.

When the run ends, the archive copies what a reading needs into a run folder on the operator's machine, load/.runs/<run id>/: the raw lines, the logs of the services that say what broke, the platform's one-minute metrics, the database's Performance Insights, and what ECS and scaling recorded. The manifest is written last and seals the run. Rebuild turns a sealed folder into numbers, a verdict and an HTML report from files alone, long after every stack and every CloudWatch point is gone.

3. The harness and its boundaries

The load harness is a workspace of its own, load/, held to the same gate as the app: typecheck, lint, comment hygiene, dependency audit, boundaries and tests. It is split by job. The boundary check (dependency-cruiser) enforces which part may import which, so that, for example, rebuild provably cannot reach AWS.

The backend's own records (exchange, job, request and state lines), the signal catalogue and the EMF helper live in the shared lib/ workspace, because the backend may not import the harness. Both sides read and write the same schema. The catalogue names every signal a run or a live view reads, once: its unit, where it comes from (a generator line, a backend record or an AWS metric), how a minute of it is summed, and its pass line if it has one. A new signal is added there and nowhere else, and the live dashboard and the monitor are checked to ask for nothing the catalogue lacks. The load stack itself is in infra/lib/load/, and the shell commands around a run are in infra/scripts/.

4. One aws-prod run, end to end

  1. Budget and stack. aws-prod load claims the day's worst-case cost in the spend ledger, which counts the NAT gateway, its address and every gigabyte through it. It refuses when the day would pass its limit. Then it deploys the load stack for the raised step and image tag, with the origin's ingress rule when the run takes the direct path.
  2. Open the run. The load command works out the run's limits from its step and writes .sources/raise.json into the new run folder: what the raise was made of, so the run can be archived after its stacks are gone. A run folder with no manifest is visibly unsealed, and down refuses while the raise has one.
  3. Supervise. The command's supervisor splits the users into even slices and launches one generator per slice.
  4. Run. Generators ramp, hold and stop. Every line goes to CloudWatch Logs as it is written, and its EMF block becomes metrics.
  5. Seal. Once the generators have ended, or have been stopped because the run ended early, the command seals the run. The archive waits until CloudWatch has the run's last whole minute, collects every source for the run's window and the few minutes after it, checks itself, writes the raw files, and writes the manifest last.
  6. Rebuild. The load command hands the sealed run to rebuild, which writes derived/ beside it: the verdict, the report and the tables.
  7. Tear down the generators. The shell deletes the load stack once the command has returned, because the archive reads its tasks until then. The direct path's way in goes with it.
  8. Again, by hand. aws-prod rebuild <run id> rebuilds a sealed folder at any time, with no raise. aws-prod archive <run id> seals a run that load could not, while the raise is still up.

5. Load generation

A virtual user

  • Signs in, and retries after a growing pause when it fails, so an outage slows users down rather than losing them.
  • Keeps one push stream open for as long as the run lasts, and reconnects when it drops.
  • If it is one of the step's chatting share, it opens a Thread and chats: it sends a message, reads the streamed reply, waits the think time, and goes again.
  • Keeps both its access token and its refresh token. When a call answers that the session needs refreshing, the user refreshes once, and the push stream and chat loop share that one refresh. A refresh token is spent on use, and presenting a spent one revokes the session.
  • Every request becomes one line: run, generator, attempt, user, kind, wall-clock start, time to first byte, total time, status, outcome and error code. Durations come from a monotonic clock.

A generator

  • One Node process, so one core. It runs on 1 vCPU / 4 GiB and carries about 5,000 users, so many small generators beat a few big ones.
  • Brings its users up evenly over the ramp from the moment it starts, holds them, then stops them.
  • Writes a request line per request, a state line every few seconds from three levels it keeps (users signed in, push streams open, chatters active), and one end report: its request counts by kind and its phases.
  • When it is told to stop (SIGTERM from Spot or the supervisor), it stops its users and prints its report marked interrupted. The container gets the full 120 s Spot allows.
  • On the direct path it presents its client certificate. Requests still name the public hostname, so the origin's mutual TLS and host rules hold.

6. Supervision: who watches the load, and what happens when something breaks

Supervision has four layers. Each catches what the one above it cannot.

1 · Supervisorper slice, in the harness: launch, watch, replace, give up
›
2 · Load commandstop every generator, seal, rebuild; then the shell deletes the stack
›
3 · Safety netLambda every 5 min: delete load stack at 1 h, app stack at 3 h
›
4 · Peopledashboard and monitor against the pass lines

6.1 The supervisor's decision for a slice

  • Watching. One poll of ECS every 10 s covers every task. A generator counts as launched once its task is RUNNING, so its plan counts from when it can start.
  • Timeouts. A generator that runs past its ramp and hold plus a two-minute grace is stopped as timed out.
  • Why a task stopped. ECS forgets a stopped task about an hour later. The supervisor therefore writes each task's description (stop code, reason, exit code, capacity provider, environment) into the run folder's .sources/ as soon as it stops. The archive reads it from there.
  • Interrupts. Ctrl-C or SIGTERM aborts the supervisor. It stops every generator and records each one as interrupted. The load command then seals the run as interrupted.
  • Attempts stop here. The supervisor and the launcher count attempts, and so does the archive when it seals. After that a run knows slices: users 0 to 249, held by whichever generators were running them. Each slice lists, once, the windows it was down. A window opens when its generator was told to stop, or else at its last state line, or else when its task stopped, and closes when the replacement had brought the users back over its ramp, or at the end of the hold when nothing replaced it, and never later than the end of the run. Windows that run into each other, as when a replacement is lost too, are joined into one. A generator that finished, was stopped by the guard or was stopped for the end of the run leaves no window.

6.2 The load command's guarantees

Whatever the outcome (finished, failed, or interrupted), the load command, from its own final step:

  • stops every generator still running in the load cluster, including any the supervisor lost track of, and waits for ECS to say each has stopped;
  • seals the run with its outcome and end time, then rebuilds it. A run it cannot seal is named, so the operator can resume it with aws-prod archive <run id> and then rebuild it;
  • ends with an exit status that says which it was: 0 when the run finished its plan, 130 when it was interrupted, 1 when it failed.

The shell around the command keeps what only it can do, from outside:

  • releases the run's claim on the day's budget when the run did not complete its plan;
  • deletes the load stack, and with it the direct path's way in, unless the run could not be sealed: the archive reads the stack's tasks, so that stack stays for aws-prod archive;
  • deletes the load stack at once when the command ends before its run began recording.

Seeding runs the same fleet On-Demand, replaces no generator, keeps no record, and ends the same way: a generator that stops early fails the seeding run.

An interrupted run is not thrown away. What it recorded up to the interruption is sealed, and its rebuild is a full verdict that can never be a pass, because it names the early end. Rebuild refuses a run that was never sealed, because without a manifest nothing proves its files are whole. Sealing such a run with archive marks whatever is missing as incomplete instead.

down refuses while the current raise has an unsealed run in the operator's runs folder, unless it is forced. sweep lists anything that outlived its teardown.

6.3 The safety net and the cost guard

The safety net runs every five minutes and deletes the load stack an hour after it starts and the app stack three hours after its raise, whoever forgot them. Because the direct path's ingress rule belongs to the load stack, the safety net closes the way in too, even if the operator's machine dies mid-run. Separately, each raise and each load run claims its worst-case cost in a daily ledger in the vault, and a claim that would pass the day's limit is refused. A load run that does not complete its plan releases its claim: the claim stays in the ledger, marked, and no longer counts toward the limit, because a cancelled run rarely costs its worst case. Every later claim and status still show it, because it may have cost something. reset-budget clears the day by hand. Generators are priced at Spot; a fallback to On-Demand costs more for as long as it runs.

The safety net does not know about runs. The app stack's database is destroyed with the stack, so a run that is not sealed before the three-hour sweep loses its Performance Insights, and ECS forgets its services' tasks. Its logs and metrics survive for a while, because their groups are retained and CloudWatch keeps its points.

7.4 Rules the archive keeps

  • Raw is written once. Raw files never change after sealing. Only derived/ is rewritten.
  • One schema version. The run folder has one version, written in its manifest. A reader refuses a folder of a version it does not know rather than guess.
  • Self-checks before sealing. The archive joins every attempt's lines into its slice's file, then checks that each generator attempt has request lines covering its active window. Each generator's line count matches its own report, where it lived to write one. Every expected service has logs and metrics. The backend's records are there. Every source could be collected, every record is valid, and every checksum matches. A run that fails a check is sealed incomplete, with the reason, and can never pass.
  • Resumable. A failed archive is run again and skips files already present with a matching checksum.

8. From records to a verdict

›
Load and validateevery file against its schema
›
Minute table and run factsone row a minute; the slices, their down windows, gaps and counts
›
Judgeby the limits the run recorded
›
Cross-checkgenerators vs load balancer vs API
›
derived/summary, verdict, report, tables
  • Files only. Rebuild imports no AWS client, so it works after every stack is gone and CloudWatch has forgotten the run.
  • The table in the middle. Rebuild reads the folder once, into a table of one row a minute and a few facts about the run: how it ended, its slices and their down windows, the gaps, and the figures the criteria judge. Judging, the cross-checks and the report read those two and go no further back, so a change to what a run collects reaches them only through the table.
  • Limits come from the manifest. A run records its limits when it begins, worked out from its step and its configuration, and is judged by them. Home steps limit host CPU, memory, first byte and errors. Smoke has none: smoke proves the tools, so it passes on its records being whole, agreeing and covering its plan. The sized steps, step10 and step50, scale their limits with the step: push streams and chatters held at least 98% of the step's through the hold, and at most 2.5 s chat first byte p95, 0.5% gate waits at the limit, 0.5% sign-in failures and 70% generator CPU. A run that recorded no limits, or one no criterion judges, is still rebuilt, and its verdict says it could not be judged. There is no judging an old run by newer limits: a run is read as it was run.
  • Gaps are explicit. A slice that was down, or a source that went silent, is named with its window. It is never filled or averaged over. The windows come from the manifest, and every reader leaves out the same ones: a slice's own requests inside its down window, and the minutes it was down, are left out of the criteria and the cross-checks rather than failing them.
  • Cross-checks. The generators' answered requests are set against the load balancer's per-minute answer counts, and their errors against its error counts. The balancer counts a request in the minute it ends, so the generators' requests are counted by the minute they ended in. The API's exchange lines are set against the generators' chats: replies that streamed against exchanges that sent a first token, and paused chats against paused exchanges. A mismatch beyond tolerance makes the verdict incomplete, because one of the two records cannot be trusted. The load-balancer checks are skipped on the Cloudflare path, where the edge sits between the two records, and on cubi, which has no balancer.
  • Three outcomes. pass, fail (a criterion missed, or the guard stopped the run on one), or incomplete (something needed is missing, unreadable or contradicted).
  • Outputs. summary.json (every count and percentile), verdict.md (each criterion, gaps, cross-checks), report.html (one offline page with charts of what users and the app saw and of the infrastructure, pass lines and shaded gaps), metrics.tsv (one row a minute) and events.log (one timeline).
  • Deterministic. The same folder gives byte-identical output. Tests rebuild small fixture run folders and check their verdicts and determinism, not stored output.

10. Why it is shaped this way

A capacity run exists to answer five questions, and four of them are exactly what an operator asks in a production incident: did the load arrive, did users get a good service, where is the limit, and did capacity follow the load. The fifth, whether the reading can be believed, belongs to tests alone. That observation drives most of the shape.

The app's records come first. A signal an incident would need is written by the app or the platform, where it also exists in production, and the harness reads it rather than measuring its own.
The generator measures only what a client can see: end-to-end timings, failures as users meet them, and how much load it is actually applying.
A run lives on the operator's machine. There is one copy of a run, in one place, sealed by its manifest. Nothing has to be uploaded, fetched or kept in step with a bucket.
The way in lives as long as the load stack. One address, one rule, owned by the stack: nothing to open per generator, nothing to close by hand, and the safety net closes it too.
Rebuild from files alone. A sealed folder turns into the same verdict on any machine, long after the stacks are gone. Judging never imports an AWS client.
Raw written once, manifest last. Checksums and the seal are cheap, and they are what make a run trustworthy.

Left out on purpose

Each of these was collected once and is no longer, because nothing a capacity reading depends on was lost with it. They should not come back without a reading that needs them.

  • The database's message, usage and gate-verdict rows, and the tunnel that read them.
  • The load balancer's access logs in the run folder; they stay in the vault where the balancer writes them.
  • CloudFormation stack events, and copies of the Ari/Load and Ari/App metrics, whose lines are kept.
  • The web server's, mock's, VPC flow and warm-up log groups; they stay in CloudWatch for a month.
  • The generators' running totals and histograms; the request lines are the one count of requests.
  • On cubi, the cost-per-user shape with its process and Postgres samples.
