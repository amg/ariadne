aws-prod architecture: Cloudflare, AWS and the services

What aws-prod is made of and how its parts connect. How it is raised, tested and recovered is in aws-prod-deployment.html; how load runs are driven, supervised, recorded and judged is in load-testing-architecture.html; the decision behind it is ADR 0014. How work and news move inside the app, on any deployment, is in background-work.md. <project> below stands for the operator's AWS_PROD_PROJECT.

1. The short version

The hostname (AWS_PROD_HOSTNAME) is a proxied record at Cloudflare pointing at a public AWS load balancer. Nobody reaches the load balancer except Cloudflare, and Cloudflare forwards only the operator and the current run's load generators. Cloudflare and the load balancer prove themselves to each other with two certificates, one in each direction, both made when core is set up.

There is no tunnel and no second CDN: Cloudflare handles public HTTPS and the allow-list, the load balancer sends /api/* to the backend and everything else to nginx. Behind it, the API and a separate worker share Postgres and Valkey; the auth core and inference (mocked during load tests) are their own services, resolved directly through AWS Cloud Map private DNS without an internal load balancer.

Cloudflare is defined by Terraform, AWS by CDK. Everything lives in aws-prod's own AWS account in ap-southeast-2, in three lifetimes: core stays, app exists while aws-prod is up, load runs generator tasks in a separate stack and VPC during a run.

The API and the worker never talk to each other directly. The API queues work in Postgres; the worker picks it up and announces the result through Valkey, which the API copy holding the user's request is listening to. The worker takes no requests from the load balancer.

Every service is its own, sized on its own

Each box is an ECS service with its own task definition, task size and count. The API, the worker and mock inference are built from the same backend image but each starts its own command: the API runs migrations and then server.aws.js, the worker worker.js, the mock mock/server.ts. The auth core is SuperTokens' own server, the same container the single-server setup runs; the backend talks to it through the supertokens-node library. Per step, in tasks × vCPU per task:

There is no rate limiting in aws-prod. The backend's AWS entry point (server.aws.ts) turns the app's limits off and leaves them to the edge, and the edge's sign-in limit is off because the Free plan can't hold it to this hostname or let the generators through. The allow-list is the only gate. That holds while it stays on, and Terraform refuses to switch it off unless the edge limit is on; opening aws-prod to the public needs a rate limit back first.

4. One message, step by step

  1. The browser posts to /api/threads/:id/chat. Cloudflare checks the allow-list and forwards it over strict TLS, presenting the client certificate.
  2. The load balancer verifies the certificate, matches the host and the /api/* path, and picks an API task.
  3. The API verifies the session (the auth core holds the signing keys), stores the arrival and queues its judgment in one Postgres transaction. It subscribes to the user's Valkey channel before the commit.
  4. A worker task picks up the job, asks the mock for an embedding (and, if needed, a judge or rewrite call), commits the verdict, then publishes it to Valkey.
  5. The API task holding the request hears the verdict and streams the mock's reply back through the load balancer and Cloudflare. The browser's push stream, held on any API task, hears the title and Fact news later.

5. Why Valkey

With several copies of the API and the worker, the code that produces news and the code waiting for it usually run in different processes. Three things must cross between them:

MessageFromTo
A verdictthe worker that judged the arrivalthe API copy holding the chat request that waits on it
A finished or failed capturethe worker that ran itthe API copy holding a waiting Handover
A user's news and stopsany copyevery API copy holding that user's tabs, or their running Exchange

Valkey pub/sub carries all three, on one channel per user, so a message reaches only the copies holding that user. It keeps nothing: Postgres stays the only record, and anyone waiting re-reads it, so a lost message costs promptness, never correctness. A deployment that names no Valkey keeps the bus inside one process, as the single server does.

AlternativeWhy not
Sticky sessions at the load balancerThey pin a browser's own requests to one API copy, but most news starts on a worker, which cannot know which copy holds the user. They would help only the stop, and not across devices or deploys.
Postgres LISTEN/NOTIFYNo new service, but every commit that sends a notification takes one exclusive lock shared by the whole Postgres server and holds it until the commit is durable, so notifying commits run one at a time. The queue already pays that for every new job it inserts; push events would more than double it.
Polling the database while a request waitsSlower by the poll interval, and many queries a second per waiting chat at the target load. Push to tabs would need polling too.

The decision and its failure rules are in ADR 0012.

6. The two certificates

All the keys are generated by Terraform on the operator's machine and kept in Terraform's state, in the vault bucket (encrypted, no public access). Cloudflare's Origin CA only signs; it never sees a private key.

CDKToolkit is what cdk bootstrap creates, once per account and region: a bucket for templates and file assets, an ECR repository for image assets, and the roles CDK uses to publish, look up and deploy, including the CloudFormation execution role stacks are created through. aws-prod creates the permissions boundary that fences those roles itself, before bootstrapping. The Cloudflare zone and API token are set up by hand. The app root takes over the zone's http_config_settings, http_request_firewall_custom and http_ratelimit rule phases; a zone has one of each, so a raise is refused if anything else already owns one.

9. The backend this shape needs

  • The API and the worker run apart. The AWS entry point serves the API only and refuses to start without Valkey; the worker is its own process, chosen by PROCESS_ROLE.
  • News and stops cross copies over Valkey (section 5).
  • Thread passes hold no connection across inference. They commit optimistically, so only connections doing work count against the database's limit (ADR 0011).
  • One pending reply per Thread is enforced by the database, so two copies cannot start the same Exchange.
  • A worker frees only jobs whose lock outlived the task time limit, which only a crashed or frozen worker leaves, so many workers can share the queue.
  • Rate-limit counters stay per process, and aws-prod runs with them off (section 3).
