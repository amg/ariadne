aws-prod architecture: CloudFront, AWS and the services

What aws-prod is made of and how its parts connect. How it is raised and run is in infra/README.md; how load runs are driven, supervised, recorded and judged is in load-testing-architecture.html; the decision behind it is ADR 0014, and the one behind its front door ADR 0018. How work and news move inside the app, on any deployment, is in background-work.md. <project> below stands for the operator's AWS_PROD_PROJECT.

1. The short version

The hostname (AWS_PROD_HOSTNAME) is a DNS-only record at Cloudflare pointing at a CloudFront distribution. CloudFront ends users' TLS, and its web ACL lets in only the operator and the current raise's load generators, and limits sign-ins per address. It caches the web app's static files by their own Cache-Control, and passes /api/* through uncached. Behind it is a private load balancer with no public address, which CloudFront reaches through a VPC origin, over plain HTTP inside AWS.

Users, the operator and the load generators all come in the same way, through CloudFront. The load balancer sends /api/* to the backend and everything else to nginx. Behind it, the API and a separate worker share Postgres and Valkey; the auth core and inference (mocked during load tests) are their own services, with no internal load balancer. The API reaches auth through ECS Service Connect: a proxy beside each API task knows every healthy auth task and picks one for each request, so auth tasks added under load take their share. Inference is found through AWS Cloud Map private DNS.

AWS is defined by CDK. Terraform holds the hostname's record at Cloudflare, and the certificate with the record that proves it to ACM. Everything lives in aws-prod's own AWS account in ap-southeast-2, except what CloudFront takes only from us-east-1: the certificate and the web ACL. There are three lifetimes: core stays, app exists while aws-prod is up, load runs generator tasks in a separate stack and VPC during a run.

The API and the worker never talk to each other directly. The API queues work in Postgres; the worker picks it up and announces the result through Valkey, which the API copy holding the user's request is listening to. The worker takes no requests from the load balancer.

Every service is its own, sized on its own

Each box is an ECS service with its own task definition, task size and count. The API, the worker and mock inference are built from the same backend image but each starts its own command: the API runs migrations and then server.aws.js, the worker worker.js, the mock mock/server.ts. The auth core is SuperTokens' own server, the same container the single-server setup runs; the backend talks to it through the supertokens-node library. Each step's sizes live in infra/config/steps.ts.

Most load steps fix every count before the run starts. Long-lived connections never move to new tasks, so the API is sized for the run's target rather than left to react. step-prod, which runs no load, scales the API, the worker and the auth core on CPU instead, and scale10 rehearses that scaling under a load that rises, holds and falls.

3. The way in, and its checks

A request meets these in order. The edge's web ACL decides who gets in, and the network does the rest: the load balancer has no public address, so nothing outside AWS can reach it at all.

Sign-ins are limited at the edge. The backend's AWS entry point (server.aws.ts) turns the app's own limits off and leaves them to the edge, which counts sign-ins per address and lets the load generators past by their run key. The app's limit would count every generator's thousands of users against one address.

4. What the edge changes during a surge

Every new user opens a TCP connection and a TLS handshake. Without an edge, each of those lands on the load balancer, which grows to meet them and can lag behind a surge: in 20261031T040409Z, 27,076 sign-ins never got a connection while it grew from about 30 to about 560 capacity units.

What the edge does not change: push streams. An open push stream holds one connection from CloudFront to the load balancer for as long as it lives, so 50,000 streams are still about 50,000 connections there, opened as users arrive. A stream cut while the load balancer grows is still cut. The browser reconnects within the stream's random retry: delay, and on connect the stream resends the user's current state, so nothing is lost. A run records how many streams were cut and how fast they came back.

5. One message, step by step

  1. The browser posts to /api/threads/:id/chat. CloudFront ends its TLS, checks the web ACL, and forwards it uncached through the VPC origin, on a connection it already holds open.
  2. The load balancer matches the host and the /api/* path, and picks an API task.
  3. The API verifies the session (the auth core holds the signing keys), stores the arrival and queues its judgment in one Postgres transaction. It subscribes to the user's Valkey channel before the commit.
  4. A worker task picks up the job, asks the mock for an embedding (and, if needed, a judge or rewrite call), commits the verdict, then publishes it to Valkey.
  5. The API task holding the request hears the verdict and streams the mock's reply back through the load balancer and CloudFront. The browser's push stream, held on any API task, hears the title and Fact news later.

6. Why Valkey

With several copies of the API and the worker, the code that produces news and the code waiting for it usually run in different processes. Three things must cross between them:

MessageFromTo
A verdictthe worker that judged the arrivalthe API copy holding the chat request that waits on it
A finished or failed capturethe worker that ran itthe API copy holding a waiting Handover
A user's news and stopsany copyevery API copy holding that user's tabs, or their running Exchange

Valkey pub/sub carries all three, on one channel per user, so a message reaches only the copies holding that user. It keeps nothing: Postgres stays the only record, and anyone waiting re-reads it, so a lost message costs promptness, never correctness. A deployment that names no Valkey keeps the bus inside one process, as the single server does.

AlternativeWhy not
Sticky sessions at the load balancerThey pin a browser's own requests to one API copy, but most news starts on a worker, which cannot know which copy holds the user. They would help only the stop, and not across devices or deploys.
Postgres LISTEN/NOTIFYNo new service, but every commit that sends a notification takes one exclusive lock shared by the whole Postgres server and holds it until the commit is durable, so notifying commits run one at a time. The queue already pays that for every new job it inserts; push events would more than double it.
Polling the database while a request waitsSlower by the poll interval, and many queries a second per waiting chat at the target load. Push to tabs would need polling too.

The decision and its failure rules are in ADR 0012.

7. The certificate

One certificate, for the hostname, which CloudFront presents to every browser and generator. The last hop, from CloudFront to the load balancer, never leaves AWS, so it carries no TLS and needs no certificate.

Proved bya DNS record in Cloudflare's zone, kept there so ACM renews the certificate on its own
Presented bythe distribution, which reads its ARN from SSM at each raise
Keptwith core: it costs nothing, and a raise never waits on issuance

At each raise the edge rules come first, then the app stack and its distribution, then the hostname's record. A teardown runs the other way, and deleting the distribution, which must be disabled first, takes some minutes.

10. The backend this shape needs

  • The API and the worker run apart. The AWS entry point serves the API only and refuses to start without Valkey; the worker is its own process, chosen by PROCESS_ROLE.
  • News and stops cross copies over Valkey (section 5).
  • Thread passes hold no connection across inference. They commit optimistically, so only connections doing work count against the database's limit (ADR 0011).
  • One pending reply per Thread is enforced by the database, so two copies cannot start the same Exchange.
  • A worker frees only jobs whose lock outlived the task time limit, which only a crashed or frozen worker leaves, so many workers can share the queue.
  • Rate-limit counters stay per process, and aws-prod runs with them off, leaving sign-ins to the edge (section 3).
