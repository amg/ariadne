aws-prod deployment: commands, steps, testing and recovery

How aws-prod is raised, run, torn down and recovered, and how it is checked. What it is made of is in aws-prod-architecture.html; the decision behind it is ADR 0014. Run scripts/aws-prod for the commands and scripts/aws-prod <command> --help for any one of them.

1. The scripts

CDK defines AWS and Terraform defines Cloudflare. A few bash commands in infra/scripts/ run them in order, carry the values one side needs from the other, and check what neither can.

5. Rollback: AWS does, Cloudflare doesn't

rolls back CDK / CloudFormation

  • If any resource fails, CloudFormation undoes the whole deploy.
  • A failed update returns to the previous state.
  • A failed creation leaves an empty stack in ROLLBACK_COMPLETE; CDK deletes and recreates it on the next deploy.
  • A service that never turns healthy rolls its own deploy back (ECS circuit breaker).

no rollback Terraform, and the scripts

  • Terraform keeps whatever it created before the error, recorded in its state in the vault. Applying again finishes the job; destroying removes what exists.
  • The scripts stop at the first failure and undo nothing themselves.

6. When something fails

Run up <step> again. If the app stack is already up at that step, up resumes: it keeps the raise's images and run key, doesn't record the spend a second time, and repeats every later step, each safe to repeat. A raise at a different step is refused until you run down.
A resumed raise keeps the images it already built. If the fix is a code change, run down first.

7. The safety nets

NetWhat it doesWhat it doesn't
Scheduled function in core, every 5 minutes deletes the app stack 3 hours after it was created, and the load stack after 1 hour. A resumed raise keeps its first creation time touch Cloudflare: a record left behind serves errors until the next down or up
Daily worst-case ledger every raise and load run records the most it could cost before the safety net deletes it; past $100 in a day, the next is refused read the AWS bill, which lags by hours

8. How it is checked

Without an account

Any change to infra/ can be checked locally: npm run check typechecks the package and synthesizes every stack at every step, and terraform validate runs on both Cloudflare roots. The exact commands are in infra/README.md. The load generator runs under plain Node against any server.

On every raise, by the commands themselves

  • before-raise refusals, the spend ledger, and CloudFormation's health waits with rollback;
  • reachable through Cloudflare, refused around it;
  • the warm-up's exit code;
  • sweep after every teardown.

9. Steps, and what each must show

The one-time setup (account, quotas, Cloudflare token) is in infra/README.md. After that the steps run strictly in order, because each run's readings set the next step's sizes.

G1, Core. aws-prod core succeeds twice in a row. Pass: certificate ARN in its parameter, CA in the vault, safety-net schedule enabled.
G2, Seed. aws-prod seed. Pass: 100,000 signup.ok, near 100,000 seed.chat.streamed, snapshot available, sweep clean. Reading: seed wall time and the auth core's CPU (password hashing).
G3, Smoke and drills. aws-prod up smoke, then load. Pass: 1,000 sign-ins with no failures, push.open.peak = 1,000 and no drops, 200 chatting users with zero chat.failed. Security drills, each a pass or a stop:
  • Browse from an address not on the list (a phone on mobile data): Cloudflare blocks it.
  • curl the load balancer's DNS name directly: refused.
  • Thirty quick sign-in attempts without the run key, from an address not on the list: blocked by the allow-list (aws-prod has no rate limit to test).
  • Safety net: start a load run with a long hold and walk away. The load stack is gone at 60 minutes.
Teardown and sweep clean, then check billing the next day against the ledger.
G4, step10. Everything in G3 at 10,000 users, plus a push from the worker reaches a tab on a different API copy, and no job ever runs twice (queue failed count 0). Readings: per-task CPU and connections, Postgres commit latency under the queue's notifies, Valkey requests per second. Re-size step50 from them.
G5, step50. Same criteria at 50,000. Add: the database's connection count against its limit, and the load balancer's capacity units.
G6, step100. The target: 100,000 users holding tabs open, 20,000 chatting. Pass: p95 time to first byte held from step50, no push drops, error rate under 0.1%, and the day stays within the $100 ledger.
